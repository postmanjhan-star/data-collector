# SMT Data Collector 1.6 — operator experience
Design references: Anthropic frontend-design (https://github.com/anthropics/skills/tree/main/skills/frontend-design); Windows design guidance (https://learn.microsoft.com/en-us/windows/apps/design/guidelines-overview).
Design tokens: ink #1E2B31, muted #4A5B62, accent #0D696C, canvas #EDF2F3, line #D3DEDF, surface #FFFFFF. Traditional Chinese uses Microsoft JhengHei UI; numeric/endpoint fields use Segoe UI. Native WinForms, no extra UI runtime. Keep command strip compact and telemetry distinct from server receipts; no decorative motion, no generic dashboard gradients. Explicit labels identify raw scans, not finished boards. Do not infer a healthy broker from PUBACK.
Operator workflow: prepare offline test (new SQLite + upload disabled), start simulator, start collection, verify counts, stop both before editing settings. For MQTT use the server sync page; select protocol, set URL, unique collector ID and credential, save, probe then start collection. The probe is only broker connect/subscribe; server receipt requires real scan upload. Existing DPAPI credentials remain when changing transport; replace credentials explicitly. Never use production credentials or existing data for a simulation. Settings are disabled during collection/simulation. Existing data and HTTP behavior retained. Shadow mode only.
Validation: existing installer and self-tests; real cross-repository Soda/EMQX integration is in Soda. Manual check at 1366×768 / 100% and 125% DPI with actual Windows desktop; inspect overview, keyboard tab order, forms, and narrow-window scrolling. No claim of visual validation without screenshots.
